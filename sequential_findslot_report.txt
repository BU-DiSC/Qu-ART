================================================================================
 QuART k-fp:  Why the Sequential findSlot is Slower than the Parallel findSlot
 A profiling report + branch-misprediction explanation
================================================================================

Date      : 2026-06-02
Component : trees/QuART_kfp.h  ::  QuART_kfp<K, EvictionPolicy, SearchMode>::findSlot
Hardware  : Intel(R) Xeon(R) Gold 6442Y  (~3.6 GHz observed under load)
Build     : gcc -O3 -march=native (CMake Release), 32-bit keys (default)
Benchmark : test_kfp, K=3, three sorted BoDS streams interleaved uniformly at
            random, 95.8% of inserts classify as FP_INSERT.


--------------------------------------------------------------------------------
 0.  TL;DR
--------------------------------------------------------------------------------

* The Sequential findSlot is slower because of BRANCH MISPREDICTION, not because
  of data copying or cache misses.

* perf proves it: the Sequential and Parallel modes have an IDENTICAL L1 data-
  cache miss rate (0.14% vs 0.15%), but Sequential suffers ~35M MORE branch
  mispredictions (55.2M vs 19.7M). Each misprediction is a ~15-20 cycle pipeline
  flush.

* Root cause: the Sequential scan tests slots one at a time with a data-dependent
  early-exit branch ("does slot i match?"). Because the streams are interleaved
  uniformly at random, each key matches a random one of the 3 slots, so that
  branch is fundamentally unpredictable (~1/3 taken, no pattern).

* The Parallel mode is faster because it converts K unpredictable branches into
  K branchless comparisons + ONE highly-predictable branch ("did ANY slot
  match?", ~96% taken) + one ctz instruction to extract which slot.

* This is an information-theoretic floor. Five measured optimization attempts and
  an independent 5-agent review panel all confirmed: no change that keeps the
  scan "sequential" (early-exit) meaningfully beats it on this workload. The only
  lever (probe the last-matched slot first) helps bursty/clustered workloads but
  REGRESSES this uniform-random benchmark.

* Decision: leave the Sequential findSlot as the clean, honest baseline. The
  Parallel mode is the answer when speed matters.


--------------------------------------------------------------------------------
 1.  BACKGROUND
--------------------------------------------------------------------------------

QuART_kfp keeps K independent "fast-path slots", one per interleaved sorted
stream. On every insert, findSlot() classifies the key against all active slots
by comparing the key's upper bytes (all but the last byte) to each slot's cached
upper bytes:

    FP_INSERT  - upper bytes equal a slot's tail        -> append on that slot
    BRIDGE     - upper bytes adjacent (+/-1) to a slot  -> rebuild that slot
    NO_MATCH   - no slot claims the key                 -> allocate/evict a slot

findSlot has two implementations selected at compile time by the SearchMode
template parameter:

    Parallel    (default) - branchless K-way compare, collapsed to one branch.
    Sequential            - the classic early-exit scan: test slots one at a
                            time, stop at the first match.

The two produce identical classifications on this workload. The question this
report answers: why is Sequential slower, and can it be made faster while
remaining an early-exit scan?


--------------------------------------------------------------------------------
 2.  THE TWO CODE PATHS
--------------------------------------------------------------------------------

SEQUENTIAL (the early-exit scan; trees/QuART_kfp.h):

    for (int i = 0; i < num_active; i++) {
        if (slots[i].fp_leaf == nullptr) continue;
        key_int_t leafUpper = slots[i].cached_upper;
        if (keyUpper == leafUpper)                 // <-- unpredictable branch
            return {i, MatchType::FP_INSERT};
        if (((keyUpper + 1) & upperMask) == leafUpper ||
            ((leafUpper + 1) & upperMask) == keyUpper)
            return {i, MatchType::BRIDGE};
    }
    return {-1, MatchType::NO_MATCH};

PARALLEL (branchless K-way match; trees/QuART_kfp.h):

    unsigned match = 0;
    for (int i = 0; i < K; i++)
        match |= (slots[i].cached_upper == keyUpper) << i;   // branchless sete
    if (match != 0u)                                          // ONE branch (~96% taken)
        return {__builtin_ctz(match), MatchType::FP_INSERT};
    // (falls through to the sequential scan for warm-up / BRIDGE / NO_MATCH)

Note: K=3 is a compile-time constant, so both loops are FULLY UNROLLED by the
compiler.

--------------------------------------------------------------------------------
 5.  DIAGNOSIS
--------------------------------------------------------------------------------

The two telling facts:

  (a) The L1 data-cache miss RATE is identical (0.14% vs 0.15%). The Sequential
      scan does NOT copy structs and does NOT miss cache more than Parallel. The
      hypothesis that "copying instead of references" causes the slowdown is
      DISPROVEN by the data. (The only real copies in the insert path are in
      loadSlot/saveToSlot, and the FP_INSERT hot path already uses a reference
      'FpSlot& s = slots[slotIdx]' and skips them; they fire on only ~0.1% of
      inserts.)

  (b) The Sequential scan executes +350M more branches and, crucially, suffers
      +35.5M more branch MISPREDICTIONS. At a ~15-20 cycle flush each, that is
      roughly 35.5M * ~18 = ~640M cycles -- a large share of the 1.64B extra
      cycles Sequential spends. The remainder is the lost instruction-level
      parallelism around those flushes (IPC 2.16 vs 3.00).

Therefore: the bottleneck is BRANCH MISPREDICTION, originating in the data-
dependent early-exit branch of the sequential scan.


--------------------------------------------------------------------------------
 6.  HOW BRANCH MISPREDICTION CAUSES THE SLOWDOWN  (worked example)
--------------------------------------------------------------------------------

WHY BRANCHES NEED PREDICTION
  A modern CPU is a deep pipeline (~15-20 stages) with hundreds of instructions
  in flight. Every cycle it must know which instruction to fetch next. A
  conditional branch (an "if") depends on a comparison whose inputs may still be
  loading, so the CPU cannot wait. It GUESSES the outcome (the branch predictor)
  and speculatively executes the guessed path.
    - Guess right -> free, the pipeline never stalls.
    - Guess wrong -> it discards all speculative work and restarts from the
      correct path: a ~15-20 cycle FLUSH (~5 ns). That is one "branch miss".
  The predictor's only tool is history -- it needs a learnable PATTERN.

THE SEQUENTIAL BRANCH HAS NO PATTERN
  Three sorted streams, interleaved uniformly at random, each tracked by a slot:

      Slot 0  ->  Stream A,  cached_upper = 10
      Slot 1  ->  Stream B,  cached_upper = 20
      Slot 2  ->  Stream C,  cached_upper = 30

  Look at the first branch in the scan, at slot 0:  `if (keyUpper == 10)`.
  It is TAKEN (match found, early exit) exactly when the incoming key belongs to
  stream A -- i.e. 1/3 of the time, in no order. Trace 8 incoming keys whose
  streams arrive as: B A C A B C A A. The predictor's best strategy is to predict
  the majority outcome (not-taken, since 2/3 of keys miss slot 0):

      key from   slot-0 "==10"?   predictor guessed   result
      --------   --------------   -----------------   --------------
         B        not-taken        not-taken          correct
         A        TAKEN            not-taken          MISPREDICT (flush)
         C        not-taken        not-taken          correct
         A        TAKEN            not-taken          MISPREDICT (flush)
         B        not-taken        not-taken          correct
         C        not-taken        not-taken          correct
         A        TAKEN            not-taken          MISPREDICT (flush)
         A        TAKEN            not-taken          MISPREDICT (flush)

  4 flushes in 8 keys. No predictor can do better here: the outcome depends on
  which stream the NEXT key happens to come from -- an external coin flip with no
  correlation to anything the CPU has seen. Real predictors (TAGE, etc.) bottom
  out near the entropy floor (~1/3 mispredict on this branch).

  And because the loop is unrolled (K=3), each key runs through SEVERAL of these
  independent unpredictable branches (slot 0, then slot 1 if 0 missed, then slot
  2 if 1 missed). That is the source of the measured 55.2M branch-misses.

  Intuition: Sequential is like asking three people ONE AT A TIME "is this yours?"
  and stopping at the first yes. You can't prepare for WHEN the yes comes, so you
  flinch every time.


--------------------------------------------------------------------------------
 7.  HOW THE PARALLEL DESIGN SOLVES IT
--------------------------------------------------------------------------------

The Parallel version never branches per slot. Conceptually, for K=3:

    bit0 = (slots[0].cached_upper == keyUpper);   // branchless: cmp + sete
    bit1 = (slots[1].cached_upper == keyUpper);   // branchless
    bit2 = (slots[2].cached_upper == keyUpper);   // branchless
    match = bit0 | (bit1<<1) | (bit2<<2);
    if (match != 0) return { ctz(match), FP_INSERT };   // ONE branch (~96% taken)

Three things change:

  1. PER-SLOT COMPARISONS BECOME BRANCHLESS.
     `a == b` no longer feeds an `if`; it feeds a VALUE. On x86 this is `cmp`
     followed by `sete` (set-byte-if-equal), which writes 0 or 1 into a register
     with NO jump and NO control-flow change. There is nothing to mispredict --
     the CPU computes all three comparisons unconditionally. Because the three
     are independent (no data dependency), they issue on separate execution ports
     in the same cycles. That parallelism is what gives the mode its name.
     Result for a key from stream B: match = 0b010.

  2. THE ONE REMAINING BRANCH IS PREDICTABLE.
     `if (match != 0)` asks a DIFFERENT question: not "which slot matched?" but
     "did ANY slot match?". Since 95.8% of keys are FP_INSERT, this branch is
     taken ~96% of the time -- a near-constant outcome the predictor nails.
     Misprediction rate collapses from ~1/3 to ~1-4%.

  3. THE HARD PART IS ANSWERED BY ARITHMETIC, NOT A BRANCH.
     "Which slot?" -- the genuinely unpredictable bit -- is recovered by
     __builtin_ctz(match) (count-trailing-zeros), a single instruction returning
     the index of the lowest set bit (0b010 -> 1). No guessing.

  Intuition: Parallel shows the package to all three people AT ONCE; they answer
  simultaneously and you read off who raised a hand. The only thing you "predict"
  is "did somebody raise a hand?", and the answer is almost always yes.

THE CORE IDEA
  The unpredictable information -- WHICH of K slots matches -- is inherently
  random on this workload and can never be predicted well. The two designs differ
  in WHERE they put that information:

      Sequential : in CONTROL FLOW (a chain of data-dependent branches)
                   -> the predictor must guess random outcomes -> ~55M flushes.
      Parallel   : in the DATAPATH (branchless sete compares + ctz), leaving only
                   one PREDICTABLE branch ("any match?") -> ~20M misses, 1.37x.

  You cannot make the random "which slot" question predictable; that is the
  information-theoretic floor. The win comes from not asking it as a branch.


--------------------------------------------------------------------------------
 8.  OPTIMIZATION ATTEMPTS  (all built and measured; seq mode, 20M keys/stream)
--------------------------------------------------------------------------------

  #  Variant                                   Throughput     Branch-misses   Verdict
  -- ---------------------------------------   ------------   -------------   --------
  V0 Original (AoS, null-check, lazy bridge)   39.4 M/s        55.2 M         baseline
  V3 Branchless single combined early-exit     33.4 M/s        74.3 M         WORSE
     (compute isFp|isBridge bitwise, fold the
      empty-slot guard, one cmov early-exit)
  V1 Remove dead fp_leaf==nullptr null-check   39.6 M/s        56.2 M         neutral
  V2 Structure-of-Arrays: contiguous           37.9-39.7 M/s   55.6 M         neutral
     key_int_t slot_upper[K] (one cache line)
  H  Temporal-locality hint: probe the         36.9-38.5 M/s   58.7 M         WORSE
     previously-matched slot (active_slot)                                    (on uniform)
     first, then scan

WHY EACH FAILED OR WAS NEUTRAL
  V3  Computing the BRIDGE arithmetic eagerly for EVERY slot adds work to the
      95.8% FP_INSERT common path (+750M instructions), and the long composite
      condition delays the early-exit branch's resolution. More mispredicts, not
      fewer.
  V1  Removes a predictable branch (the null-check is dead in steady state, since
      every slot in [0,num_active) is fully populated by the time findSlot runs).
      Fewer instructions, but cycles unchanged -- the bottleneck is mispredict
      stalls, not instruction throughput. (Also reintroduces a correctness
      dependency on the invariant for zero gain, so it was reverted.)
  V2  Confirms the loads were never the problem: putting all K cached_upper values
      in one cache line does not reduce mispredictions. Branch-misses unchanged.
  H   The hint is correct only 1/3 of the time on uniform-random interleave, so it
      adds a wasted probe plus an `i == hint` skip branch -> a small regression.

  Branch-misses stay pinned near ~55M across V0/V1/V2 regardless of memory layout
  or branch structure -- the tell-tale signature of an information-theoretic
  floor.


--------------------------------------------------------------------------------
 9.  INDEPENDENT REVIEW PANEL
--------------------------------------------------------------------------------

A panel of five independent agents (micro-architecture, algorithmic, codegen,
state/hint, and wildcard lenses) each proposed one sequential-preserving
optimization; a sixth synthesized.

Verdict on the premise (verbatim): "CORRECT: Sequential early-exit on uniform-
random K=3 interleave IS fundamentally mispredict-bound ... No instruction-level
trick (cmov, loop unrolling, prefetch overlap) can reduce the misprediction COUNT
below ~50M when the data is adversarially random."

The only idea judged worth building -- probing the last-matched slot first
(temporal-locality hint) -- was assessed as: helps_uniform_benchmark = FALSE,
helps_bursty_workloads = TRUE. Direct measurement (variant H above) confirmed it
regresses the uniform benchmark.


--------------------------------------------------------------------------------
 10.  CONCLUSION & DECISION
--------------------------------------------------------------------------------

* The Sequential findSlot is slower purely due to branch misprediction inherent
  to an early-exit scan over uniformly-interleaved streams. It is NOT copying,
  NOT cache, NOT instruction count.

* On THIS benchmark the Sequential scan is already at its floor. No change that
  keeps it sequential improves it; the parallel restructuring is the only thing
  that helps, and that mode already exists.

* The one realistic lever is the temporal-locality hint, which only pays off if
  the real workload has STREAM CLUSTERING (consecutive keys from the same
  stream). The synthetic benchmark interleaves uniformly at random by
  construction, so it cannot show that win and in fact regresses ~2-6%.

* DECISION: leave the Sequential findSlot as the clean, honest baseline. Use the
  Parallel mode when throughput matters (1.37x here). If a future experiment uses
  clustered/bursty interleaves, revisit the opt-in hint as a third SearchMode.
